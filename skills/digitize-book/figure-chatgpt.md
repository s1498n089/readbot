# ChatGPT 版截圖操作（image_model=chatgpt）

> `digitize-book` §5「截圖」的 **image_model=chatgpt 分支**——透過內建 Playwright MCP 用 CDP 接管一台**已登入**的 ChatGPT，用它的視覺＋Python(PIL) 裁切、用 image-gen／PIL 生譯圖。Claude 的強項是語言，看圖／生圖的多模態交給 ChatGPT。
> **共用的部分不在這裡、在主 `SKILL.md §5`**：裁切的 4 條合格標準、§5B 回讀驗收、§5C 的「要不要生／命名／文字專項驗收」。本檔只講「怎麼操作 ChatGPT」。文中 `§5`／`§5B`／`§5C` 指主 SKILL.md 的對應節；「步驟 N」「裁切段／生譯圖段」指本檔。
> 工具名：dev=`mcp__playwright__*`、安裝後=`mcp__plugin_readbot_playwright__*`。

> 🚫🚫 **鐵律（務必遵循）：丟給 ChatGPT 一次只做一張圖——裁切、譯圖都一樣。**
> **一則訊息塞多張、或同一個對話連續追加多張，效果一定崩**（裁切→出細條／漏圖說／切到外框線；譯圖→翻錯字／漏字／圖體被畫走樣）。這是**實測反覆驗證**的結論，**沒有例外、不要抱僥倖**。
> 要一次處理多張，**唯一正確做法＝「開多分頁、每頁一張、一個對話只放一張圖」並行**（裁切見下面並行段、譯圖同理）。重點是**多開分頁**攤開跑，**絕不是**把量堆進同一個對話。**寧可慢、寧可多開幾批，也不要為了省事把多張塞進一個對話。**

## 裁切
丟「含整張圖的大圖」給 ChatGPT，讓它用視覺＋Python(PIL) 自己裁、回精準成品：
1. **前提**：CDP Chrome 開著且已登入 `chatgpt.com`。沒開先跑 `.browser/launch-chrome-cdp.bat`（見 `/readbot:setup`），確認 `http://127.0.0.1:9222/json/version` 回 200。**接不上（9222 探測失敗、或還沒登入 ChatGPT）→ 停下來，請使用者跑 `/readbot:setup` 步驟 5/6 備好 CDP＋登入 ChatGPT 後再繼續。**
2. **備輸入圖**：從該頁 PNG 切一塊**含整張圖的大略區域**存 `.browser/tmp/`。**🔑 寧可切大、絕不可切小**——這塊「粗胚」只是給 GPT 看的原料，**必須完整含整張圖＋整行圖說**；上下左右多框到正文／頁碼／別張圖**都沒關係**（GPT 之後會精準裁掉），但**只要切到圖或圖說一點點，被切掉的部分 GPT 永遠救不回來、成品必壞**。所以不必精準，寧可連上下內文一起**多框一大圈**。
3. navigate `https://chatgpt.com/` → 點 composer「＋」(`composer-plus-btn`) → 選單點「**從電腦上傳**」（**文字依 ChatGPT UI 版本而異，找「上傳／從電腦」那一項**，別寫死）→ `browser_file_upload` 那塊大略圖。備案（選單文字改版時更穩）：跳過選單、直接對頁內隱藏的 `input[type=file]` 上傳。
4. 在輸入框（`#prompt-textarea`）打**裁切指令**再送出（**送出方式見本步驟末：別按 Enter、也別用 `browser_click`**）。**固定用這個通用範本**（把 `图 X-Y` 換成實際編號；知道圖說全文就一起填進去，幫 ChatGPT 定位更準；英文書改用 `Figure X-Y`）——它已把 §5 的 4 條標準寫進去：
   > 這張圖裡有一張圖「**图 X-Y**」。請用 Python（PIL）把「图 X-Y 那張圖，加上它正下方那整行圖說『**图 X-Y …**』」精準裁切成一張 PNG。要求：
   > - ① 圖外圍那圈細細的**外框邊線要完整保留**、四邊都不可切到它、也不要讓它貼在圖片邊緣。
   > - ② 在外框線的**外側再多留一點白邊（約 20~30px）**、四周有呼吸空間。
   > - ③ **不可包含上下或旁邊的內文段落**（正文那幾行不要）。
   > - ④ **一定要含「图 X-Y …」那整行圖說**（有兩行就兩行都要）。
   >
   > 裁好後請用 **IPython.display 的 `display(Image(...))` 把成品直接內嵌顯示**出來（不要只給下載連結）。
   - 例：`X-Y`＝`1-5`、圖說填『均值为0、标准差为1的正态分布』。**外框線＋外側留白這點很重要**——光說「留白邊」GPT 常會切到框線，要明講「外框線外側再留白、別貼邊」。
   - **送出（別按 Enter、也別用 `browser_click`）**：Enter 在圖還沒傳完時不會送出；`browser_click` 點送出鍵會卡在 Playwright 的 actionability「stable」檢查（送出鍵有動畫、永遠等不到穩定）而逾時。**正解**：① `browser_type` 把指令填進 `#prompt-textarea`；② **等上傳完成**——送出鍵未就緒（`disabled`）時多等幾秒再試，別 hard-code 死等固定秒數（圖越大／連線越慢要越久，約 6 秒起跳）；③ `browser_evaluate` 點送出鍵、順便自檢就緒：
     ```js
     () => { const b = document.querySelector('#composer-submit-button');
             if (!b || b.disabled) return 'NOT_READY';   // 還在上傳，等一下再送
             b.click(); return 'clicked'; }
     ```
     ④ **確認網址變成 `/c/<id>`** 才算真的送出（沒變＝沒送出去，回 ② 再等再送）。
5. 等它跑 Python 裁好 → **先讓 GPT 自檢這張裁切、通過才抓回本機**（收成法裁切／生譯圖共用）：
   - **🔍 GPT 自檢裁切（每張必做，這關要問 GPT）**：在**同一對話**請它逐項檢查剛裁好那張圖：
     - **①** 圖的內容有沒有被切到（四邊、尤其曲線**峰頂**）？
     - **②** 最底下的圖說「图 X-Y …」完整嗎、有沒有被切半或缺字？
     - **③** 有沒有含到「圖＋圖說」以外的東西（正文段落、頁眉頁碼、別張圖）？

     逐項回答。**任一項不 OK → 在同對話請它重裁修正、再自檢，三項全過才收成**（別收被切／含雜的版本）。⚠️ **自檢只是低成本的第一道篩**——早點抓明顯截斷／夾雜（也能發現 Claude 餵的大略圖切掉了原圖），但**自檢逐項回 OK ≠ 可以免驗**（實測有「回 OK、成品卻少一整塊」的情形）；**真正守門仍是 §5B 執行者逐張回讀（強制）**。
   - **完成訊號＝頁面出現「成品 `<img>`」**，其 `alt` 有**三種**（都算完成、收成要全認）：① PIL／code interpreter 產出＝`輸出圖像`；② image-gen 重繪＝`已產生圖像：…`；③ 從**檔案卡預覽**渲染出來的＝檔名本身（如 `figX-Y_cropped.png`）。生成中時 `main img` 只有 Claude 剛上傳的原圖（alt 是原檔名）。**別靠 stop-button 判斷**——它常殘留、會誤判成「還在生成」。生成通常要 **30–90 秒**（複雜圖 >2 分鐘），所以是「`browser_wait_for` 等 25~40 秒 → `browser_evaluate` 探一次 → 沒圖再等一輪」的**輪詢**，一次沒抓到不代表失敗。
   - **卡死就放棄、別無限等**：若某分頁**一直 busy**（送出鍵持續 `disabled`／停在「正在停止思考」）**且完全沒有任何 assistant 內容**、遠超上面說的正常生成時間（拖到數分鐘、約 10 分鐘還這樣），就當**那個對話卡死**：放棄它、**開全新分頁重送完整指令**（實測重送常就成功）；**別在卡死的對話裡追加訊息**（送不出去），也別枯等。判定以「狀態」為主（busy＋零 assistant 內容），時間只是量級參考。
   - **GPT 已回完（宣稱完成／或報錯）、卻抓不到內嵌 `<img>` 時，分兩路救**（還在生成就繼續輪詢、別急著救）：
     - **有「檔案卡」→ 點開檔案卡（首選）**：GPT 把成品渲染成一張可下載的「檔案卡」（`main` 內某個 `<button>`、class 含 `group/open-file`、innerText 含 `.png`），此時沒有內嵌 `<img>`。**用 JS 點那個 `<button>`、等約 3 秒**，預覽會把成品渲染成 `<img>`（alt＝檔名，即上面第③種）→ 照樣收成。⚠️ **這張預覽 `<img>` 開在 modal、不在 `main` 底下**——收成時要把範本的 `main img` 放大成整份 `document.querySelectorAll('img')` 才抓得到。此時**別泛泛追問「請重新 `display`」**——實測會回同尺寸舊檔或空回應，**點檔案卡才是首選**。
     - **連檔案卡都沒有、只留一行 `/mnt/data/…png` 路徑**（或只顯示「發生錯誤、請重試」）→ 成品其實已存在沙盒、只是沒渲染出來。同對話送「我這邊看不到圖，請**直接執行 `display(Image('/mnt/data/…png'))` 重新內嵌一次、不要重做**」（**指名那個路徑**，這跟上面「泛泛追問」不同、可靠）→ 通常一次救回，省下整張重生一輪。
   - **收成：`fetch(img.src)` 取 blob → `a.download` 觸發下載 → 找到檔案搬進 images/**。範本：
     ```js
     async () => {
       const UPLOADED = 'crude_figX-Y.png';                // ← 換成本回合 browser_file_upload 的那張粗胚圖檔名
       // 主判準＝排除本回合上傳圖後取最後一張候選；關鍵字只降為「輔助優選」（成品檔名每次不同、白名單追不完，漏一個變體會整張抓不到還誤報還沒好）
       const cands = [...document.querySelectorAll('main img')].filter(i => i.alt && i.alt !== UPLOADED);  // 排除剛上傳的原圖（見⚠️）。走檔案卡那條路收成時，把 'main img' 改成 'img'（預覽在 modal、不在 main）
       const hit = cands.filter(i => /輸出圖像|已產生圖像|cropped|translated|_zh|繁體/.test(i.alt));
       const img = (hit.length ? hit : cands).at(-1);       // 命中關鍵字用命中的最後一張、否則退回全部候選的最後一張
       if (!img) return 'NOT_READY';                       // 還在生成／只剩檔案卡，下一輪再探或點檔案卡
       const blob = await (await fetch(img.src)).blob();
       const a = document.createElement('a');
       a.href = URL.createObjectURL(blob); a.download = 'gpt_figX-Y.png';   // 只是暫時檔名，搬完就沒了
       document.body.appendChild(a); a.click(); a.remove();
       return 'OK ' + img.naturalWidth + 'x' + img.naturalHeight;
     }
     ```
     - ⚠️ **收成前一定要先排除「本回合剛上傳的原圖」**（範本的 `UPLOADED`）：候選掃的是全部 `main img`、**含你剛上傳那張**；沒排除的話、成品又還沒生好時，上傳圖會變成**唯一候選**被 `at(-1)` 取走、函式照樣回報 `OK`，於是**靜默把原圖當成品存下去**（生譯圖尤危險：譯圖會存成與原圖一模一樣、無錯誤訊息）。上傳圖的 alt＝你上傳的檔名——別靠命名慣例擋，要在候選裡明確排除它。
     - **落點別預設**：Playwright **不一定**攔得到 `.browser/out/`（實測常沒攔到、`a.download` 落到瀏覽器預設下載夾如 `~/Downloads`；檔名底線 `_` 是否被改寫也視環境而定）。→ 下載後**實際 `ls` 找檔**：先看 `.browser/out/`、沒有再看瀏覽器下載夾，找到就用 **`mv`**（不是 `cp`）搬到 `…/images/figX-Y.png`，**別在下載夾留檔**（使用者要求圖檔別堆在下載夾）。
     - ⚠️ **同一台 Chrome 連續下載可能被 Chrome 攔阻**（「同站短時間下載多檔」的保護；**門檻視 Chrome 版本／設定而定、別當固定張數**）。**觸發依據是「下載這條路失敗」**（`mv` 前在 `.browser/out/` 與瀏覽器下載夾都 `ls` 不到剛下載的檔），不是去數張數；一旦失敗就改**不經下載夾**收成，但**別用 `browser_evaluate` 的回傳值把 base64 帶回來**（一張 700KB PNG≈95 萬字元，會塞爆 context、還可能被截斷）。正解：
       - ① evaluate 內 `fetch(img.src)`→blob→轉 base64，`return` 那串 base64；
       - ② **傳 `browser_evaluate` 的 `filename` 參數**（給了 filename ＝把回傳值**寫成檔、不灌回 context**；接受相對專案 root 的子路徑）落到 `.browser/tmp/<name>_b64.txt`；
       - ③ 本機讀該檔 → `base64.b64decode` → 寫成 `…/images/figX-Y.png`。⚠️ **`filename` 寫出的檔帶 UTF-8 BOM（外層有時多包一對 `"`）**，本機要用 `open(..., encoding="utf-8-sig").read().strip().strip('"')` 讀（用 `utf-8` 讀會因 BOM 誤判內容）；
       - ④ 中繼的 `_b64.txt` 收工前清掉（`.browser/tmp/` 已 gitignore、別留在 root）。
   - **`alt`／檔案卡是完成的主判準**；尺寸（naturalWidth）只當 fallback——譯圖尺寸常與原圖幾乎相同，比大小會誤抓（image-gen 版還常 `naturalWidth=0`，但 `fetch(img.src)` 照樣拿得到，見生譯圖段）。
6. ⚠️ 餵的大略圖若含「頁緣細框線」，ChatGPT 也會框進去——想更乾淨就餵「已不含頁緣線」的較緊區域。

**🚀 並行方式：開多分頁、每頁一張（一次最多 5 頁）＝唯一正確做法**（呼應鐵律）：兩條規則同時成立——⛔ **一個對話只裁一張圖**（多張塞同一對話品質必崩：細條／漏圖說／切外框線）＋**多張圖開多個分頁同時跑**（不必等前一張做完，5 張的生成時間幾乎重疊）。
   - **做法**（用 `browser_tabs` 管分頁）：
     - ① 開分頁，**一次最多 5 個**（`browser_tabs` action=new）。
     - ② 逐頁 select → `navigate https://chatgpt.com/`（各自全新對話）→ 上傳單張大略圖 → 下裁切指令送出，**不等結果就切下一頁送**（把 5 頁全部送出）。
     - ③ 全送出後**輪一圈**（依步驟 5）：逐頁 select → 探成品（三種 alt／檔案卡，見步驟 5）→ **先讓 GPT 自檢裁切（步驟 5🔍）、通過**再收成（`a.download` → 找到檔案 → `mv` 成 `figX-Y.png`）；`NOT_READY` 或自檢沒過的**下一輪再回來**（別死等某一頁擋住其他頁）。
     - ④ 每頁 §5B 回讀驗收。
   - ✅ **每頁一張＝來源↔成品在各自分頁一一對應**：不必靠 DOM 順序對照、不會對錯張。
   - ⚠️ **一個對話（分頁）只放一張圖**：同一對話**連續追加上傳下一張**常會「顯示卡住／只回下載連結、抓不到內嵌圖」；**把多張塞進同一則訊息叫它一次裁**則品質參差、易出細條／漏圖說／切外框線。要多做就**多開分頁**，不是把量堆進同一頁。
   - ⚠️ **一次最多 5 個分頁**：再多難管理、也吃資源。超過 5 張就**分批**（這批收完、再開下一批）。
   - ⚠️ 備輸入大略圖時**範圍要夠（含整張圖＋下方整行圖說＋周邊一點白，讓 GPT 有空間保住外框線）**；抓太小會出「細條」或「漏圖說」。§5B 驗到就**單獨開一頁重裁**。

## 生譯圖
（要不要生、命名、看板對照、文字專項驗收都在主 §5C；這裡是 chatgpt 版「怎麼生」的操作。）
- **流程＝接在裁切後**，每張圖「**先裁切 → 再生譯圖**」：把剛裁好的 `figX-Y.png` 丟 ChatGPT，要求「**把圖內文字＋圖說翻成目標語言，其餘（圖形／座標軸／數據／曲線／數學符號／排版／配色）維持原樣**，重新輸出整張圖」。**預設做法＝請 GPT 用影像生成「重新繪製整張圖」（image-gen），這是優先選擇**——對結構／示意圖（流程圖、金字塔、漏斗、節點圖、方框圖…）最乾淨、文字換得徹底、不會有殘字問題（GPT 常自己就走這條）。**只有少數圖種要改走 PIL 疊字**（照片／勾勾／精確 code／數據曲線——見下方💡）。**建議範本**（`[…]` 換成該圖實際內容；照 §4a 用語；數學符號與變數、產品名不翻）：
   > 這張圖裡有簡體中文文字。**請用你的影像生成能力「重新繪製」整張圖**、把圖內的簡體中文文字和最底下的圖說換成繁體中文——**不要用 PIL 在原圖上疊字**（純結構圖用疊字會蓋壞版面、殘留原文字尾）。重要：除了中文詞換繁體，其餘一切（`[數學符號、箭頭、神經網路方塊、配色、排版]`）盡量保持原樣。文字對照（簡→繁）：`[训练数据→訓練資料；图 X-Y …→圖 X-Y …]`。完成後用 IPython.display 的 `display(Image(...))` 內嵌顯示，不要只給下載連結。
   - **文字對照要含圖說中文版照抄**（最準）；純翻圖說的圖（框內無可翻文字）就點明「圖體維持原樣、只翻最下／旁那行圖說」。
   - **image-gen 也要「明講」——別靠它自己會走**：實測不寫明時，GPT 對純結構流程圖常自作主張改用 PIL 疊字、把版面蓋壞（`output_text` 標籤被白塊整塊蓋掉、方框線被蓋斷、右緣殘留原英文字尾），補一句「改用影像生成重繪、別再疊字」重下一次才乾淨。所以範本已把「用影像生成重繪、不要疊字」寫死進去——和下方 💡「走 PIL 要明講並講理由」兩邊對稱。
   - 💡 **改走 PIL 疊字的時機＝image-gen 會「動到不該動的東西」的那幾類圖**（**只有這些才用 PIL，不是預設**）：
     - ① **照片／第三方 UI 截圖**（image-gen 會把人臉／內容／截圖整個重畫，真人照變成 AI 生成、截圖被畫走樣，整張圖失去意義）。
     - ② **勾勾／標記**（重繪常漏畫）。
     - ③ **精確 code／hex／數字**（重繪可能改字）。
     - ④ **數據圖／曲線**（重繪對不上原數據）。

     這幾類才明講「**務必用 code interpreter＋PIL 在原圖上疊字覆蓋、絕對不要用影像生成重畫**」，並**把理由一起講**（GPT 才乖乖走 PIL），PIL 能像素級零改動、也不缺字（`x_t`、`ε_θ`、全形標點都出得來）。⚠️ **PIL 疊字自己的毛病**：遮蓋色塊常只按「譯文寬度」開，**譯文比原文短時右緣會殘留原文字尾**（例：Problem-Solver 只蓋一半、露出 `er`）→ 同對話請它「**把每條的遮蓋色塊加寬到蓋掉整段原文、再重新輸出**」。
- **🚀 並行方式同裁切段——譯圖也絕對是「一個對話一張圖」（呼應鐵律）**：⛔ **絕不可**把多張圖丟同一個對話叫它一次翻，也**絕不可**在同一對話連續追加下一張——**多張一起翻＝翻錯字／漏字／圖體走樣，效果超差**。要翻多張就**開多分頁、每頁一張、一次最多 5 頁**（超過就分批）：逐頁全新對話→上傳單張原圖＋該圖文字對照→下譯圖指令並要求 `display(Image(...))` 內嵌顯示→全部送出後**輪一圈收成**（用裁切段步驟 5 的共用收成法，但譯圖預設走 image-gen：`alt` 判完成的辨識見下、收成後找到檔案 `mv`、`NOT_READY` 下一輪再回來），存成 `figX-Y.<語言碼>.png`。特有兩點：
   - **收成辨識**：同步驟 5 的**三種 alt**——`已產生圖像：…`（image-gen 重繪，譯圖預設走這條）／`輸出圖像`（PIL 疊字）／檔名（檔案卡預覽，如 `figX-Y_zh.png`），取**最後一張**（GPT 常迭代多版），尺寸只當 fallback。⚠️ **image-gen 的 `<img>` 常 `naturalWidth=0`（沒渲染進畫面），canvas 抓不到、但 `fetch(img.src)` 照樣拿得到 blob**——收成一律走 `fetch(img.src)`（步驟 5 範本就是這招），別靠 canvas。
   - **修字錯在「同一頁的同對話」內做**：某頁譯圖驗出字錯，就在**那一頁**點名要它改哪個字、重新輸出——「別追加」限制的是**別張新圖**，修同一張不受限。重生次數上限見主 §5C「文字專項驗收」。
- **image-gen 重繪對結構／示意圖很忠實**（版面、配色、圖示都照原圖）——這正是預設用它的原因；會「跟原圖對不上」的只有**數據圖／曲線／照片／勾勾／精確數字**那幾類，那幾類才改走 PIL（見上💡）。
